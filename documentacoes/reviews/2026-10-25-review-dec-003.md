## Achados

### REVIEW-001 — MEDIO (dados/migrations) — atomicidade por migration depende de convencao nao verificada
`runner.mjs:60-62` — `await client.query('BEGIN'); await client.query(m.sql);`
- Cenario (reproduzido): migration `CREATE TABLE b1(x int); COMMIT; CREATE TABLE b2(x int); SELECT 1/0;`. O `COMMIT` interno encerra a transacao do runner; `b1` fica persistida, a versao nao e registrada, o erro volta. Resultado: `b1` existe, `schema_migrations` sem a versao. Reexecutar falha para sempre em `relation "b1" already exists` — tenant preso, exigindo intervencao manual. O mesmo ocorre com qualquer comando que encerre transacao ou que nao possa rodar nela.
- Risco: o ADR-017 e o procedimento afirmam "falha faz ROLLBACK completo"; isso so vale se o arquivo obedecer a regra "nao use BEGIN/COMMIT", hoje so textual (passo 4 do procedimento). Em lote com N tenants, o primeiro tenant quebra o lote (fail-fast) com estado meio aplicado.
- Plano: (a) ADR-017: registrar como requisito do runner de producao uma verificacao estatica que rejeita `BEGIN|COMMIT|ROLLBACK|SAVEPOINT|CREATE INDEX CONCURRENTLY` (e `VACUUM`) em migrations nao marcadas como "sem transacao"; (b) apos `m.sql`, conferir `SELECT txid_current_if_assigned()`/`pg_current_xact_id_if_assigned` ou o estado via `client.query('SELECT now() = transaction_timestamp()')` nao e suficiente, preferir o lint estatico; (c) teste em `poc.mjs` com a migration acima exigindo rejeicao antes de executar. Risco da mudanca: baixo.

### REVIEW-003 — BAIXO (seguranca/qualidade) — ADR afirma allowlist para nomes de database/role, mas `provision()` nao a aplica; hooks de teste na API do runner
- `poc.mjs:25-33`: `provision(names)` usa `escapeIdentifier` mas nao chama `assertDbName` antes de `DROP DATABASE ... WITH (FORCE)` / `CREATE DATABASE`. Na PoC os nomes sao constantes; porem o ADR (decisao 2, ultimo item) descreve "allowlist + escapeIdentifier" como contrato do provisioner e o unico provisioner demonstrado nao o cumpre (`DROP ... FORCE` e a operacao mais perigosa). Plano: chamar `assertDbName` em `provision` e em um teste negativo.
- `runner.mjs:41,106`: `failAfter` e `holdMs` (ganchos de teste) fazem parte da assinatura publica de `migrateTenant`. Se o runner for promovido a producao (ADR menciona), isso permite induzir falha por configuracao. Plano: ADR/DAT registrar que sao exclusivos de teste (ou injetar via funcao de teste separada).

### REVIEW-004 — BAIXO (robustez) — mascaramento de erro
`runner.mjs:72-74` — `catch (e) { await client.query('ROLLBACK'); throw e; }`: se a conexao caiu, `ROLLBACK` lanca e substitui o erro original, perdendo a causa no relatorio de falhas do lote. `finally` ja engole erro de unlock (correto). Plano: `await client.query('ROLLBACK').catch(() => {})` e registrar a causa original; teste matando a conexao (`pg_terminate_backend`) no meio.

### REVIEW-005 — BAIXO (compatibilidade) — checksum sobre texto decodificado
`runner.mjs:23-29`: checksum = SHA-256 da string utf8. Fim de linha CRLF (checkout Windows com autocrlf) ou BOM mudariam o checksum de arquivo identico em Git e fariam o runner abortar em tenants ja migrados. Nao ha `.gitattributes` na PoC. "Precisa de validacao": nao reproduzido. Plano: ADR exigir `*.up.sql text eol=lf` e hash sobre bytes (`readFileSync` sem encoding); teste com CRLF.
